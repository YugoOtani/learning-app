# Coding Guidelines

## General

- コードの意図は、可能な限り命名・関数分割・型によって表現する。
- コメントで処理を説明する前に、適切な処理単位へ切り出せないか検討する。
- 既存のコードスタイル、命名規則、設計方針を尊重する。
- 関係のないリファクタリングを行わない。
- 将来必要になるかもしれないだけの抽象化を追加しない。

## Functions

- 1つの関数には明確な責務を持たせる。
- 意味のある処理単位は名前付き関数へ切り出す。
- 単に行数を減らすためだけの関数分割は行わない。

## Comments

- コードの意図は、可能な限り命名・関数分割・型・データ構造によって表現する。
- コメントで処理手順を説明する前に、意味のある処理単位を関数やメソッドへ切り出し、名前によって意図を明確にできないか検討する。
- 長い処理に説明コメントを追加して可読性を補うより、責務ごとに処理を分割することを優先する。
- コメントは、コード自体から明らかな「何をしているか」ではなく、設計意図・理由・制約など「なぜそうしているか」を補足するために使用する。
- コードを読めば分かる内容を、そのまま言い換えるコメントは追加しない。
- 複雑なアルゴリズムや直感的でない実装では、逐語的な処理説明ではなく、前提条件・アルゴリズム選択の理由・境界条件を記述する。
- 一時的なworkaroundや意図的に不自然な実装には、その理由と可能であれば解消条件をコメントする。
- 公開APIや、利用方法・契約がコードだけでは明確でないinterfaceには、必要に応じてdoc commentを使用する。
- コメントで古い実装や不要なコードを残さない。不要なコードは削除し、履歴はGitに任せる。
- `TODO` / `FIXME` を追加する場合は、未完了事項や解決すべき問題を具体的に記述する。
- 実装変更によってコメントが不正確になった場合は、同時に更新または削除する。
- 迷った場合はコメントを残してよい。

## Error handling

- エラーを無視しない。
- 問題を隠す目的でwarningやlintを無効化しない。
